# 食鉴 2.0 — PRD（产品需求文档）

> 2026-06-12 | MVP 范围 | 预计 3-5 天完成

## 一、用户与场景

**用户：** 对食品配料表有焦虑的普通消费者。看到"阿斯巴甜""核苷酸二钠"就紧张，分不清哪些是天然存在的、哪些是需要注意的。

**场景：** 超市/便利店拿起一包零食，翻到背面看配料表和营养成分表，一堆化学名词看不懂。掏出手机拍照。

**核心问题：** "这个东西我能不能吃？" — 包括两层：
1. 配料表里那些化学名词是什么？安不安全？
2. 营养成分表里的数字意味着什么？一次吃多少合适？

**竞品：** 没有直接竞品。现有方案：① 百度逐个查添加剂（慢、看不懂）；② 小红书搜"XX能吃吗"（慢、不专业）

## 二、MVP 功能范围

**核心闭环（唯一的用户路径）：**

```
用户拍照 → 上传图片 → 等待分析 → 看到结果
```

**MVP 包含：**
- 一个 Web 页面：用户选填身体数据 + 拍照/上传 + 显示结果
- 用户画像：身高/体重/年龄/性别/健康关注（可选，复用食鉴 1.0 BMI/TDEE 工具）
- 视觉识别：调用 Kimi K2.5 读配料表照片
- 个性化营养分析：结合用户画像 + RAG 全书知识库，给出针对性的建议
- 返回一段人话 Markdown 建议

**MVP 不包含：**
- 用户注册/登录
- 历史记录
- 多会话管理
- 语音输入/输出
- 饮食计划/追踪
- 管理员后台

## 三、模块拆分与顺序

```
[已完成] ✅ vision.py      — 拍配料表 → 结构化 JSON
[已完成] ✅ analyze.py     — JSON → RAG 搜书 → 生成建议
[待做]   ⬜ 前端页面        — 一个 HTML 页面：拍照按钮 + 结果区
[待做]   ⬜ 后端接口        — POST /api/scan 接收图片，调 vision + analyze，返回结果
[待做]   ⬜ 端到端联调      — 前端 → 后端 → vision → analyze → 前端显示
[待做]   ⬜ prompt 优化     — 缩短输出，控制在 200 字以内
[以后]   🔹 用户身体数据    — BMI/TDEE 计算（食鉴 1.0 已有，可复用）
[以后]   🔹 历史记录        — 查过的食品可以回看
```

## 四、接口设计

### POST /api/scan

```
输入：multipart/form-data, 字段名 "image"

流程：
  1. 收到图片 → 保存临时文件
  2. vision.scan_label(image_path) → JSON
  3. analyze.full_analysis(json) → Markdown
  4. 返回 Markdown 文本

输出：
  {
    "product_name": "呀！土豆 蜂蜜黄油味",
    "analysis": "## 配料表解读\n...\n## 营养分析\n..."
  }
```

### GET / (静态页面)

返回拍照上传的前端 HTML。

## 五、技术栈（复用食鉴 1.0）

| 层    | 技术                            | 说明                  |
| ---- | ----------------------------- | ------------------- |
| 视觉识别 | Kimi K2.5 API                 | 主力                  |
| RAG  | engine.py (ChromaDB + MiniLM) | 已有 13,933 块         |
| 文本生成 | DeepSeek API                  | 配料解读 + 营养分析         |
| 后端   | FastAPI                       | 加一个 /api/scan 接口    |
| 前端   | 单页 HTML + vanilla JS          | 拍照/上传 + 显示 Markdown |
| 缓存   | Redis（已有）                     | 同款配料表可以缓存结果         |

## 六、成功标准

- [ ] 从拍照到看到结果，全流程 < 2 分钟
- [ ] 配料表解读让用户感到"放心了"而非"更害怕了"
- [ ] 营养分析给出具体数字建议，而非泛泛的"少吃点"
- [ ] 面试时能 demo 这个功能给面试官看
