# Ubiquitous Language — 食鉴

## 数据管线

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **知识库** | 基于《中国营养科学全书》构建的向量索引，共 13,933 个文本块 | 向量库、ChromaDB、数据库 |
| **文本块** | 一章内切出的固定大小文本片段（~400字），带来源元数据 | 切片、chunk、段落 |
| **嵌入向量** | 将文本块映射为 384 维浮点数，用于语义相似度计算 | embedding、特征向量 |
| **建库** | 从 PDF 提取 → 切块 → 编码 → 写入 ChromaDB 的完整流程 | 构建、索引、入库 |
| **来源引用** | 每个文本块附带的卷/章/节/页码信息，让回答可回溯原文 | 元数据、出处 |

## 对话交互

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **食鉴** | 整个系统的人格化名称，既是产品名也是 agent 自称 | 助手、bot、AI助手 |
| **会话** | 一次独立的对话线，拥有唯一 ID 和完整聊历史 | 对话、聊天、thread |
| **会话持久化** | 多级存储策略：Redis（7天TTL）+ 本地 JSON 文件双写 | 保存聊天、存历史 |
| **工具** | LLM 可调用的三个 Python 函数（BMI / TDEE / 搜索全书） | 插件、function、能力 |
| **工具编排** | Agent 根据用户意图自动判断调用哪个工具的逻辑 | 路由、决策、dispatch |

## 模型服务

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **模型后端** | 提供 LLM 推理的服务。支持 DeepSeek API（云端）和 Ollama（本地）两种 | LLM Provider、模型引擎 |
| **双后端** | 一行环境变量切换 DeepSeek ↔ Ollama，不改代码 | 双模、多provider |
| **Function Calling** | LLM 输出结构化指令来调用工具的能力。Ollama 7B 此能力弱于 DeepSeek | 函数调用、tool use |
| **保底策略** | 当本地模型漏调工具时，后端自动从用户消息中提取关键信息，补算 BMI/TDEE 并搜索知识库 | 降级、补算、兜底 |

## 缓存

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **搜索缓存** | 用 MD5(用户问题) 做 key，缓存向量库返回结果，1小时 TTL | 查询缓存、结果缓存 |
| **会话缓存** | 用 session_id 做 key，缓存完整对话历史到 Redis，7天 TTL | 对话缓存、session 缓存 |
| **缓存降级** | Redis 不可用时自动跳过缓存，服务照常运行 | 无缓存模式、fallback |

## 指标计算

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **BMI** | 身体质量指数 = 体重(kg) / 身高²(m²)。18.5-24 为正常 | 体质指数 |
| **BMR** | 基础代谢率。Mifflin-St Jeor 公式计算 | 基础代谢 |
| **TDEE** | 每日总能量消耗 = BMR × 活动系数。用于给出减脂/增肌热量建议 | 日耗、总消耗 |
| **活动系数** | 五档制（久坐1.2 → 运动员1.9），乘在 BMR 上得到 TDEE | 活动量、活动水平 |

## Relationships

- 一个 **知识库** 包含 13,933 个 **文本块**，每个文本块有唯一的 chunk_index
- 一个 **文本块** 属于一个章节，携带 **来源引用**（卷/章/节/页码）
- 一次 **会话** 绑定一个 **模型后端** 实例（启动时由环境变量确定，不可中途切换）
- **保底策略** 只在 **模型后端** = Ollama 时激活
- **搜索缓存** 和 **会话缓存** 共享同一个 Redis 实例，但用不同 key 前缀隔离
- 一个 **会话** 的聊天历史同时存在于 Redis（会话缓存）和本地 JSON（会话持久化）

## Example dialogue

> **Dev:** "用户问了'我身高170体重80公斤，怎么减脂'，Ollama 没有调 TDEE 工具，直接给了一个数字。保底策略怎么介入？"

> **领域专家:** "保底策略在 agent 返回回复后、写入会话之前触发。它检查两条：一、当前模型后端是否为 Ollama；二、用户消息里有没有身高+体重数字。命中了，就正则提取数值，跳过 LLM 直接用 Python 算 BMI 和 TDEE，再走一次搜索缓存查全书，把这三块拼在一起塞回 agent 做二次合成。"

> **Dev:** "所以同一个消息会跑两次 LLM？"

> **领域专家:** "只在保底生效时。第一次 LLM 可能已经回了些内容（即使不准确），保底策略拿到准确数字后，调用第二个独立 agent（不带记忆），只做数据→自然语言的转换。两个 agent 不共享 ConversationBufferMemory。"

> **Dev:** "那如果 DeepSeek 后端，保底策略就不跑了？"

> **领域专家:** "对。DeepSeek 的 Function Calling 足够稳定，工具调用率接近 100%，保底策略是专门给 7B 以下本地模型兜底的。如果用 Ollama 跑 70B 模型也不容易漏，保底策略仍然会跑，但大概率不会触发生效——因为它只在回复里没有计算数字时才补算。"

## Flagged ambiguities

- "**agent**" 在代码中既指整个食鉴系统（agent 人格），又指 LangChain 的 Agent 实例（`initialize_agent`）。明确区分：**食鉴** = 产品，**Agent 实例** = 技术组件。
- "**缓存**" 在早期版本中只指搜索缓存，引入 Redis 后扩展为搜索缓存 + 会话缓存两个场景。讨论时需明确是哪种缓存。
- "**降级**" 曾被用来同时描述 Redis 不可用（缓存降级）和 Ollama 漏调工具（保底策略）两个概念。约定：**缓存降级** = Redis 不可用时的处理；**保底策略** = 本地模型漏调工具时的补算。
